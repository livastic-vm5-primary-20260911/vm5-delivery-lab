Read the approval before anyone signs it.

ERC-20 calldata preflight decodes one unsigned transfer or allowance-changing call into its method, address arguments and raw integer amount. It flags approve(spender, 2²⁵⁶−1), which may grant a spender an effectively unlimited token allowance. Your token's deployed code, transaction state and chain are not checked. One reproducible example

An ERC-20 approve(address spender,uint256 amount) call begins with selector 0x095ea7b3, followed by a 32-byte padded spender address and a 32-byte integer. The sample below approves the illustrative dead address for the maximum possible unsigned 256-bit integer.

Included methods

  • transfer(address,uint256) — recipient and atomic amount.
  • approve(address,uint256) — spender and atomic amount, with a maximum-allowance warning.
  • transferFrom(address,address,uint256) — sender, recipient and atomic amount.
  • increaseAllowance(address,uint256) / decreaseAllowance(address,uint256) — change in raw allowance, not the actual on-chain allowance.

Important limits: Selector collisions, malicious custom token implementations, NFT methods, permit, token metadata, decimals, revocations, spender identity and actual allowance balances are not verified. A warningCount=0 result is not proof a transaction is safe. Decode locally or read the open-source implementation if you do not need a hosted, paid HTTP response.

Already have an ERC-20 receipt event log, not a transaction call?

The distinct ERC-20 Transfer / Approval event-log decoder is designed for a different ABI surface: four public 32-byte words (topic0, topic1, topic2, and data) from a canonical 3-topic ERC-20 log.
