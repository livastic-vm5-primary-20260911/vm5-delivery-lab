USEFUL SIGNALS, NOT CLAIMS OF DELIVERY

Three public DNS questions an operator can review

MX — Where could mail go?

List advertised mail exchangers. A listed MX does not establish that a mailbox exists or that mail will be accepted. No MX record alone is not universal proof of failure; SMTP has specific fallback behavior.

SPF — Is an authorization policy published?

Identify the existence of a v=spf1 TXT policy. A string existing is not enough to prove correct syntax or alignment. Multiple SPF policies and too many DNS lookups merit a separate standards-aware review.

DMARC — What policy is requested?

Inspect published _dmarc policy values such as p=none, quarantine or reject. A requested DNS policy is not evidence that a specific sent message passes SPF/DKIM alignment.

WHAT WE WILL NOT PRETEND

Published DNS is not inbox deliverability

Not checked

Mailbox existence, SMTP handshake, DKIM selector validation, SPF/DKIM pass for a particular message, actual spam-folder placement, user consent, or whether a person will reply.

Operational caveats

DNS may be cached, change after inspection, or use split-horizon/private resolvers. This is a bounded public-data preflight, not a continuous monitor or security/compliance certification.

Privacy and consent

Only pass a public domain you may inspect. The sample page runs as static HTML with no JavaScript, tracking or input collection. An independently chosen paid request sends the public domain to the API for DNS lookup; don't send personal emails or private account details.
